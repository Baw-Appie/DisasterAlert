# 브랜치 전략, PR 규칙 및 태스크 보드 운영 (GIT_AND_PR_RULES)

본 문서는 팀 **undefined (2인)**의 GitHub 협업 일관성을 유지하고, 평가 항목인 **이슈·PR 기록**, **기간 전체의 고른 커밋 분포**, **마감 시각 준수**를 보장하기 위한 규칙입니다.

---

## 1. 작업 기본 흐름 (Issue-Driven Workflow)

모든 코드 변경(iOS 및 Node.js 서버 모두)은 반드시 아래 5단계를 거칩니다. `main` 브랜치에 직접 커밋(Direct Push)하는 것은 엄격히 금지합니다.

```text
1. GitHub Issue 생성 & GitHub Projects 보드 등록
   ↓
2. 이슈 기반 작업 브랜치 생성 (feat/#8-keyword-priority-filter)
   ↓
3. 작은 단위로 구현 & SwiftLint / 서버 린트 통과 확인 후 커밋
   ↓
4. Pull Request 생성 (시뮬레이터 캡처/GIF 첨부 + 셀프 체크)
   ↓
5. 상대 팀원(1명) 코드 리뷰 Approve 확인 후 Squash and Merge
```

---

## 2. 브랜치 전략 (GitHub Flow 기반)

언제든 클론하여 바로 빌드·시연할 수 있는 `main` 중심 브랜치 전략을 사용합니다.

### 브랜치 종류 및 네이밍
- **`main`**: 항상 실행 가능한 안정 브랜치 (Branch Protection 적용)
- **작업 브랜치**: `<type>/#<이슈번호>-<짧은-영문-케밥케이스-설명>`
  - `chore/#1-init-ios-swiftlint` (iOS 초기 세팅 및 SwiftLint 적용)
  - `feat/#3-safetydata-nodejs-sync` (Node.js 재난안전데이터 공유 플랫폼 연동)
  - `feat/#8-keyword-priority-filter` (포함 우선 키워드 및 위급재난 선택 옵션 구현)
  - `feat/#12-swiftui-search-view` (다조건 검색 SwiftUI 화면 구현)
  - `fix/#16-corelocation-denied-state` (위치 권한 거부 시 처리 수정)

## 3. Pull Request 및 2인 팀 코드 리뷰 규칙

### 3.1 PR 작성 원칙
1. **작은 PR 유지**: 상대 팀원이 빠르게 파악할 수 있도록 **한 PR당 변경 라인 수 300~400줄 이내**(Xcode 프로젝트 자동 생성 파일·`package-lock.json` 제외)를 권장합니다.
2. **단일 목적 준수**: 하나의 PR에는 하나의 이슈만 해결합니다. iOS 화면 구현과 대규모 백엔드 리팩토링을 한 PR에 섞지 않습니다.
3. **시각 자료 첨부**: SwiftUI UI 변경이 포함된 PR은 시뮬레이터 스크린샷 또는 동작 GIF를 첨부합니다. *(발표 자료 시연 에셋으로 재활용)*

### 3.2 머지 및 승인 규정
- **최소 승인 인원**: 작성자 외 **상대 팀원 1명 Approve 필수**
- **머지 전 필수 조건**: `SwiftLint` 경고/에러 0건 확인(iOS 변경 시) 및 서버 린트/테스트 통과 확인(Node.js 변경 시)
- **머지 방식**: **Squash and Merge** 기본 사용 (`main` 히스토리를 이슈 단위로 깔끔하게 유지)
- **머지 후 정리**: 머지 완료된 작업 브랜치는 즉시 삭제합니다.

### 3.3 리뷰 코멘트 우선순위 태그
- `[P1 - 필수 수정]`: 크래시 위험(강제 언래핑 등), 필터 정책(`포함 우선` 등) 오동작, 예외 상태 누락 등 반드시 수정 후 머지해야 하는 사항
- `[P2 - 권장 제안]`: SwiftUI 뷰 분리, 가독성, 쿼리 개선 등 수정을 권장하는 사항
- `[P3 - 사소한 의견 / 질문]`: 단순 궁금증이나 참고용 의견 (수정하지 않아도 머지 가능)

## 4. 태스크 보드 운영 규칙 (GitHub Projects)

두 팀원이 서로의 진행 상황(iOS / Node.js)과 병목을 한눈에 파악하도록 **GitHub Projects (Kanban Board)**를 운영합니다.

| 컬럼 | 의미 및 이동 조건 |
| :--- | :--- |
| **Backlog** | 구현 예정인 전체 기능 및 고도화 아이디어 목록 (P1 포함) |
| **Todo** | 이번 주에 구현하기로 합의되었고 담당자가 배정된 이슈 |
| **In Progress** | 현재 브랜치를 생성해 작업 중인 이슈 *(1인당 동시 진행 이슈는 최대 2개로 제한)* |
| **In Review** | PR이 생성되어 상대 팀원의 코드 리뷰를 기다리거나 반영 중인 상태 |
| **Done** | 리뷰 승인 후 `main` 브랜치에 머지 완료된 작업 |
