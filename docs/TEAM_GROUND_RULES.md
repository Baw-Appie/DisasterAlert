# 팀 그라운드 룰 및 필수 진행 습관 (TEAM_GROUND_RULES)

본 문서는 팀 **NULL (2인)**이 프로젝트 시작 전 합의하는 **그라운드 룰·역할 분담**과, 프로젝트가 끝날 때까지 매일·매 PR·매주 반복하는 **다섯 가지 협업 습관** 및 **의사결정 기록(ADR)**을 정의합니다.

---

## 1. 소통 및 협업 그라운드 룰

| 항목 | 규칙 내용 |
| :--- | :--- |
| **팀명 / 구성** | **NULL** (2인 팀) |
| **공식 연락 채널** | 팀 지정 메신저 채널 (업무 논의, 스탠드업, PR 알림을 단일 채널로 일원화) |
| **메시지 응답 기한** | 코어 타임 내 **2시간 이내**, 코어 타임 외 **6시간 이내** 확인 (즉시 답변이 어려우면 확인 이모지 또는 답변 가능 시각 먼저 공유) |
| **정기 회의 및 주간 회고** | 매주 1회 정기 회의 (주간 KPT 회고 및 다음 주 스프린트 이슈 배정) |
| **지각 및 불참 처리** | 시작 **최소 2시간 전** 사유 공유 필수. 사전 공유 없는 지각 발생 시 해당 회의록 및 의사결정 기록(ADR) 정리 담당 |

### 기본 소통 태도
1. **사람이 아닌 코드와 문제를 중심으로 논의합니다.** 피드백은 구체적인 근거와 대안을 함께 제시합니다.
2. **구두 합의도 반드시 기록으로 남깁니다.** API 스펙 변경이나 필터 정책 합의는 GitHub Issue, PR 코멘트, 또는 본 문서 하단 의사결정 기록에 남깁니다.
3. **일정 지연 징후는 조기에 공유합니다.** 마감일이 지난 뒤 보고하지 않고, 지연이 예상되는 시점에 즉시 범위를 조율합니다.

## 2. 2인 팀 역할 분담 및 의사결정 체계

### 2.1 담당 영역 배정표
2인 팀의 강점을 살려 클라이언트(iOS SwiftUI)와 백엔드(Node.js) 및 기능 도메인을 명확히 분담하되, 모든 PR은 상호 코드 리뷰를 통해 두 사람 모두 전체 코드베이스를 이해하도록 운영합니다.

| 구분 | 담당자 | 주 책임 영역 | 상호 리뷰어 |
| :--- | :--- | :--- | :--- |
| **팀장 / 역할 A** | `[팀원 1 이름 기입]` | 일정·태스크 보드 총괄, `[담당 영역 기입: 예) iOS SwiftUI 화면 및 도메인 로직 / 또는 기능 분담]` | `[팀원 2]` |
| **역할 B** | `[팀원 2 이름 기입]` | 품질·문서 총괄, `[담당 영역 기입: 예) Node.js 서버 & 재난안전데이터 연동 및 iOS 검색/위치 기능]` | `[팀원 1]` |

### 2.2 의견 충돌 시 최종 결정 원칙
1. **15분 타임박스 논의**: 의견이 갈릴 경우 두 팀원이 각 대안의 구현 비용과 사용자 경험 장단점을 최대 15분간 비교합니다.
2. **결정 기준 및 최종 결정권자(DRI)**:
   - 기술 구현 세부사항은 **해당 영역(iOS / Node.js 서버)의 주 담당자**가 우선 결정권을 가집니다.
   - 프로젝트 범위·일정과 직결된 사안은 **팀장**이 MVP 마감(12월 20일) 준수 가능성을 기준으로 최종 결정합니다.
3. **결정 후 일관된 실행**: 합의된 내용은 의사결정 기록(ADR)에 이유를 남기고 같은 방향으로 빠르게 실행합니다.

## 3. 진행하는 동안 지키는 5가지 필수 습관

한 번 정해 두고 코드 제출 마감일(12월 20일)까지 예외 없이 반복합니다.

### 습관 1. 데일리 스탠드업 (매일 15분 이내)
- **원칙**: 매일 정해진 시각에 아래 세 가지만 공유하며 **15분 이내**에 끝냅니다. API 스펙 조율 등 긴 논의는 스탠드업 직후 별도로 진행합니다.
- **공유 양식**:
  ```markdown
  - 어제 한 일: (#이슈번호 포함 완료/진행 작업)
  - 오늘 할 일: (#이슈번호 포함 오늘 PR 목표 작업)
  - 막힌 점(Blocker): (없음 / 30분 이상 막힌 이슈 공유)
  ```

### 습관 2. 상호 코드 리뷰 (작고 빈번한 PR)
- **2인 팀 원칙**: 본인이 작성한 PR은 반드시 **상대 팀원 1명의 리뷰 및 Approve**를 받은 뒤 머지합니다.
- **PR은 작게 자주 올립니다.** 기능·화면·API 엔드포인트 단위로 잘게 쪼개어 1~2일 주기로 PR을 올립니다. *(기간 전체에 걸친 고른 기여도 확보 및 병합 충돌 방지)*
- 상대방이 PR을 올리면 작업 흐름이 끊기지 않도록 **24시간 이내**(마감 주간 **6시간 이내**) 리뷰합니다.

### 습관 3. 도움 요청 규칙 (30분 블로커 룰)
- **혼자 붙잡는 시간 상한은 30분입니다.**
- 재난안전데이터 공유 플랫폼 API 파싱 이슈, SwiftUI 상태 바인딩 문제, 환경 오류 등으로 **30분 이상 진전이 없으면** 즉시 아래 양식으로 팀원에게 공유합니다.
  ```markdown
  [도움 요청]
  1. 하려던 작업: (예: 재난안전데이터 공유 플랫폼 응답의 시/군/구 문자열 분리)
  2. 발생한 문제: (에러 메시지 또는 예상과 다른 결과)
  3. 30분간 시도해 본 것: (확인한 공식 문서, AI 질문 내역 및 시도한 코드)
  ```

### 습관 4. 주간 회고 (KPT 방식)
- **주기**: 매주 정기 회의 시 20분 진행
- **방식**: **KPT (Keep / Problem / Try)** 방식으로 기록하고, **Try 중 최소 1개는 다음 주 작업 방식에 즉시 적용**합니다.

### 습관 5. 의사결정 기록 (ADR)
- 아키텍처 선택이나 도메인 정책을 정할 때 **"왜 그렇게 정했는지"**를 아래 섹션에 누적 기록합니다.

## 4. 누적 의사결정 기록 (Architecture & Product Decisions)

### [ADR-001] 재난안전데이터 공유 플랫폼 연동을 위한 별도 Node.js 서버 구축 (2026-11-25)
- **배경**: 재난안전데이터 공유 플랫폼에서 재난문자 데이터를 가져와 iOS 앱의 맞춤 필터링 및 다조건 검색(날짜·지역·재난 종류·단어)에 활용해야 함.
- **검토 대안**: 1) iOS 앱에서 외부 공공 API 직접 호출 / 2) 별도 Node.js 서버를 구축해 데이터 수집·정제 후 자체 API 제공
- **결정 및 이유**: **대안 2(Node.js 서버 구축) 채택**. 공공 API 인증키를 클라이언트에 노출하지 않고 안전하게 관리할 수 있으며, 비정형적인 재난문자 본문·지역 문자열을 서버에서 일관되게 정제·인덱싱하여 iOS 앱의 다조건 검색 응답 속도와 안정성을 높일 수 있음.

### [ADR-002] 키워드 충돌 시 '포함 키워드 우선' 및 '위급재난 예외 사용자 선택권' 부여 (2026-11-25)
- **배경**: 하나의 재난문자에 포함 키워드와 제외 키워드가 동시에 존재할 때의 판별 기준과, 위급재난 문자의 필터 예외 처리 방식 확정 필요.
- **결정 및 이유**:
  1. **포함 키워드 우선**: 사용자가 명시적으로 관심 등록한 주제가 제외 키워드 때문에 가려져 안전 정보를 놓치는 상황을 방지하기 위해 **포함 키워드를 우선 적용**함.
  2. **위급재난 예외 사용자 선택 제공**: 위급재난 예외 여부를 일률적으로 강제하는 대신 설정에서 **사용자가 직접 선택(On/Off)**하게 하여, "수신 범위를 사용자가 스스로 설계한다"는 DisasterAlert의 핵심 철학을 일관되게 유지함.

### [ADR-003] 실시간 푸시 알림 기능의 추후 제공 분리 (2026-11-25)
- **배경**: 제한된 기말 프로젝트 기간(12월 20일 마감) 내에 2인 팀으로 높은 완성도를 확보해야 함.
- **결정 및 이유**: APNs 인증서 구성 및 실시간 발송 스케줄러 대신, 핵심 가치인 **관심 지역·키워드 맞춤 필터링, 현재 위치 기반 조회, 과거 재난문자 다조건 검색, 상세 확인**의 완성도를 극대화하고 실시간 푸시 알림은 추후 제공 기능으로 분리함.
